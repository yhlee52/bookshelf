Chapter 13

도구를 호출하는 모델

1~12장의 모델은 컨텍스트를 읽고 글을 쓰는 것으로 끝났다. 11장은 정답이 컨텍스트에 들어와야 한다는 조건에서 출발했고, 12장은 들어온 정보를 모델이 어떻게 쓰는지 보았다. 그런데 컨텍스트에 사실을 들여오는 일, 곧 재고를 조회하고 파일을 읽는 일은 모델이 할 수 없다. 모델이 내는 것은 토큰이고, 그 토큰이 바깥 세계의 행동이 되려면 누군가가 그 글을 읽어 실행해야 한다. 이 장의 질문은 모델이 도구를 부르는 장면에서 무엇이 모델의 일이고 무엇이 모델 바깥의 일인가이다. 13.1절은 도구 호출을 '약속된 형식의 글을 하네스가 읽어 실행하는 약속'으로 정의하고, 정답이 나오기까지의 단계(호출을 낸다, 스키마에 맞다, 인자가 맞다, 도구가 성공한다, 결과를 읽는다)를 깔때기로 나누어 11장의 식을 도구에 옮긴다. 13.2절은 인자의 값이 어디서 오는지에 따라 달라지는 상한, 스키마가 보증하는 것과 보증하지 않는 것, 같은 컨텍스트를 만드는 두 세계를 모델이 구분할 수 없다는 관측 동일성을 다룬다. 13.3절은 오류를 종류별로 나누고 재시도가 어떤 실패에서만 도움이 되는지, 오류 메시지가 어떤 정보를 실어 나르는지 계산한다. 13.4절은 읽기 도구와 쓰기 도구를 부작용으로 가르고, 응답이 유실된 쓰기를 다시 부르면 효과가 겹치는 이유를 센다. 마지막 실험은 작은 조회·예약 도구가 오류를 돌려줄 때 작은 언어모델이 재시도하는지, 지어내는지, 쓰기를 겹치게 하는지 잰다. 이 장은 14장(행동 루프), 19장(도구와 MCP), 24장(권한)의 바탕이다.

  • 도구 호출을 '모델의 출력 글, 하네스의 파서와 실행, 컨텍스트로 돌아오는 결과 글'로 나누어 설명하고, 호출이 정답으로 이어지는 단계를 곱으로 계산할 수 있다.
  • 도구 인자의 값이 컨텍스트에서 복사되는지, 유도되는지, 추측되는지에 따라 정확도의 상한이 어떻게 달라지는지, 그리고 스키마 강제(strict)가 보증하는 것과 보증하지 않는 것을 구분할 수 있다.
  • 같은 컨텍스트가 같은 행동을 만든다는 관측 동일성으로, 결과에 키를 싣지 않은 도구의 잘못된 성공과 일시·영구 실패의 첫 오류를 모델이 구별할 수 없는 이유를 설명할 수 있다.
  • 일시 실패의 재시도 성공 확률과 기대 호출 수, 영구 실패에서 같은 호출을 되풀이하는 낭비, 틀린 인자에서 오류 메시지가 운반하는 정보를 계산할 수 있다.
  • 읽기 도구, 멱등 쓰기, 비멱등 쓰기를 구분하고, 응답이 유실된 쓰기를 재시도할 때의 중복 횟수와 그것을 막는 설계(멱등 키, 확인 후 재시도)를 설명할 수 있다.
  • 도구가 오류를 돌려줄 때의 모델의 반응(재시도, 인자 수정, 지어내기, 쓰기 중복)을 조건을 바꿔 재는 실험을 설계하고, 모델이 하지 않은 것까지 결과로 해석할 수 있다.

모델 출력과 외부 행동

모델의 출력은 토큰의 열이다(1장). 모델은 파일을 열지도, 재고를 조회하지도, 예약을 만들지도 못한다. 도구 호출(tool call)은 이 사실을 다음 약속으로 우회한다. 모델이 약속된 형식의 글을 내면, 모델 바깥의 프로그램이 그 글을 읽어 함수를 실행하고, 결과를 다시 컨텍스트에 붙여 모델을 다시 부른다. 이 프로그램을 이 책은 하네스(harness)라 부른다. 모델을 호출하고, 출력을 해석하고, 도구를 실행하고, 대화를 이어 붙이는 프로그램 전체이다. 모델의 관점에서 호출도 결과도 모두 컨텍스트의 글이다. 모델은 도구가 실행되는 것을 보지 못하고, 실행의 결과가 글로 돌아오는 것만 본다.

Claude API에서 이 약속은 다음 모양이다(Tool use with Claude, Handle tool calls, 2026년 11월 확인). 요청의 tools에 도구의 name, description, input_schema(JSON Schema)를 주면, Claude는 도구가 필요하다고 판단한 턴에 stop_reason: "tool_use"로 멈추고 tool_use 블록(id, name, input)을 낸다. 하네스는 그 도구를 실행해, 다음 요청의 user 메시지에 tool_result 블록(tool_use_id, content, 선택 항목인 is_error)으로 돌려보낸다. 문서는 도구가 사용자의 애플리케이션에서 실행되는 client tools와 Anthropic의 인프라에서 실행되는 server tools(web_search 등)를 나눈다. 이 장이 다루는 것은 하네스가 실행하는 client tools이다. 이 장의 실험은 같은 구조를 Qwen의 <tool_call> JSON 형식으로 재현하며, 메시지가 오가는 순서와 각 단계의 책임은 같다.

왜 이런 우회가 필요한가. 11장의 정리가 답이다. 정답이 가중치에 닿지 않는 사실(오늘 재고, 사내 문서)이면 컨텍스트 없이는 찍는 수준을 넘을 수 없고(정리 11.1), 정확도를 올리는 길은 정답에 대한 정보가 컨텍스트로 들어오는 것뿐이다. 도구의 읽기는 그 정보를 들여오는 통로이고, 도구의 쓰기는 세계를 바꾸는 통로이다. 모델이 이 약속을 지키도록 만드는 방법도 연구되었다. Schick 외(Toolformer)는 모델이 어떤 API를 언제, 어떤 인자로 부를지, 결과를 이후 예측에 어떻게 반영할지를 API마다 몇 개의 시범만으로 스스로 배울 수 있다고 보고했다(초록). 반대쪽 증거도 있다. Patil 외(Gorilla)는 GPT-4가 API를 부를 때 정확한 입력 인자를 만들지 못하고 API 사용법을 틀리게 지어내는 경향이 있다고 지적했다(초록). 호출은 학습할 수 있는 능력이면서, 틀릴 수 있는 출력이다.

도구, 호출, 파서

도구 \(f\)는 입력 스키마 \(\mathcal A_f\)(허용되는 인자 객체의 집합)를 가진, 하네스 쪽의 함수이다. 결과는 글로 돌아오고, 실패도 오류 결과(글)로 돌아온다. 모델이 낸 출력 \(y\)에 하네스의 파서 \(\pi\)를 적용하면 \(\pi(y)\in\{\text{호출}(f,a),\ \text{글},\ \bot\}\)이다. \(\bot\)은 호출처럼 보이지만 형식이 깨진 출력이다. \(\pi(y)=\text{호출}(f,a)\)이면 하네스는 \(r=f(a)\)를 실행해 \(r\)을 컨텍스트에 덧붙이고 모델을 다시 부른다. 외부 세계에 일어나는 일, 곧 효과는 \(f\)의 실행에서만 일어난다. 모델의 출력만으로는 아무 일도 일어나지 않는다.

이 정의가 나누는 것은 책임이다. 모델은 \(y\)를 정한다. 하네스는 \(\pi\)로 \(y\)를 해석하고, \(a\)가 스키마에 맞는지 검사하고, \(f\)를 실행하고, 결과를 컨텍스트에 돌려준다. 도구는 \(f(a)\)를 계산하고 효과를 낸다. 그러므로 호출이 정답으로 이어지는 길에는 단계가 여럿이고, 각 단계의 실패는 다른 곳에서 고친다. 11장이 RAG를 색인·검색·선택·답변으로 나눈 것과 같은 방식으로 나눈다.

호출 깔때기

질문의 답을 아는 데 필요한 사실 \(x\)(예: 어떤 SKU의 재고)를 읽는 도구 \(f\)가 있다고 하자. 다음 사건을 정의한다.

  • \(C_1\): 모델이 호출을 낸다(\(\pi(y)\)가 호출이다).
  • \(C_2\): 호출의 인자가 스키마에 맞는다(\(a\in\mathcal A_f\)).
  • \(C_3\): 인자의 값이 맞다. 곧 \(a\)가 \(x\)를 담은 레코드를 가리킨다.
  • \(C_4\): 도구가 그 레코드를 돌려주며 성공한다.

\(I=C_1\cap C_2\cap C_3\cap C_4\)를 '정답이 식별되는 결과가 컨텍스트에 들어왔다'는 사건으로 정의한다(11장의 정의 11.4의 \(I\)와 같은 역할이다). 마지막 단계 \(C_5\)는 모델이 그 결과를 읽어 답하는 일이고, \(I\)일 때의 정확도 \(a_I\)가 잰다.

호출 깔때기: 고칠 곳은 가장 작은 단계이다

사실 \(x\)가 \(V\)가지 값에 균등하고, \(\bar I\)일 때 컨텍스트가 \(x\)에 대한 정보를 담지 않는다고 하자.

  1. \(\Pr[I]=p_1p_2p_3p_4\)이다. \(p_k=\Pr[C_k\mid C_1,\dots,C_{k-1}]\)이다.
  2. 모델이 \(\bar I\)에서 어떻게 하든 정확도는 \(\mathrm{Acc}=\Pr[I]\,a_I+\Pr[\bar I]\,a_{\bar I}\le\Pr[I]\,a_I+(1-\Pr[I])/V\)이다. 읽기를 완벽하게 만들어도(\(a_I=1\)) \(\Pr[I]+(1-\Pr[I])/V\)를 넘지 못한다.
  3. \(\bar I\)에서 값을 말하는 답은 \(1/V\) 이하의 확률로만 맞는다. \(V\)가 크면 거의 항상 틀린 값을 자신 있게 말하는 지어낸 답(fabrication)이다. \(\bar I\)에서 값을 말하지 않고 실패를 보고하는 답은 이 오류를 내지 않지만 정확도에 더하는 것이 없다(정확도 0도 위 상한 안에 있다).
  4. 첫 호출이 정답 레코드를 담을 수 없는 시행(인자가 틀렸거나 도구가 반드시 실패하는 첫 호출)에서 \(I\)가 일어나려면 호출이 두 번 이상이어야 한다. 그러므로 그런 조건에서 정답이 도구 결과에서 온 시행은 모두 호출이 2번 이상이다.
증명

1번은 확률의 연쇄 법칙이다. 2번은 전체 확률 공식에 \(a_{\bar I}\le1/V\)를 넣은 것이다. \(\bar I\)에서 컨텍스트가 \(x\)와 독립이면 어떤 독자의 답도 \(x\)와 독립이어서 맞힐 확률이 \(\sum_a\Pr[\hat a=a]\,\Pr[x=a]=1/V\)이다(정리 11.1의 1번, 이 값이 정리 11.4의 \(\kappa\)이다). 3번은 같은 논리이다. 4번은 \(C_3\)와 \(C_4\)가 모두 성립하는 호출이 하나도 없는 시행에서는 정답 레코드가 컨텍스트에 들어올 수 없다는 뜻이다.

어느 단계를 먼저 고칠 것인가

(가상의 값) \(p_1=0.98\), \(p_2=0.97\), \(p_3=0.95\), \(p_4=0.90\), \(V=900\), \(a_I=0.95\)라 하자. \(\Pr[I]=0.813\)이고 정확도의 상한은 \(0.813\times0.95+0.187/900=0.772\)이다. 한 단계씩 완벽하게 고치면 상한은 \(C_1\)에서 0.788(+0.016), \(C_2\)에서 0.796(+0.024), \(C_3\)에서 0.813(+0.041), \(C_4\)에서 0.858(+0.086)로 오르고, 읽기 \(a_I\)를 1로 올리면 0.813(+0.041)이다. 곱이므로 가장 낮은 단계의 개선이 가장 크다. 이 예에서는 도구의 실패(\(p_4\))를 줄이는 것이 모델의 읽기를 고치는 것의 두 배 효과이다. 실패가 많은 도구를 두고 프롬프트를 다듬는 것은 가장 작은 지렛대이다.

의 3번이 이 장 전체의 출발점이다. 도구가 실패했을 때 모델이 할 수 있는 것은 두 가지이다. 다시 부르거나(13.3절), 값을 지어내거나, 실패를 보고한다. 값을 지어내는 것은 정확도를 올리지 못하고 틀린 값을 만든다. 같은 맥락에서 Claude API 문서는 필수 인자가 빠진 요청에서 Claude Sonnet이 요청되지 않은 값을 추측해 채울 수 있고 Opus는 빠진 인자를 알아채 되물을 가능성이 훨씬 높지만 이 행동이 보장되지는 않는다고 쓴다(Tool use with Claude, 2026년 11월 확인). 이 서술은 \(C_3\)가 모델의 성향에 달려 있다는 것을 제공자가 인정한 것이다.

에이전트의 모든 행동은 파서를 지난다

에이전트가 파일을 고치고 명령을 실행하는 것은 모델이 그것을 하기 때문이 아니라, 모델이 낸 글을 하네스가 도구 호출로 읽었기 때문이다. 이 구분은 두 가지를 정한다. 첫째, 행동의 안전은 모델의 선의가 아니라 하네스가 어떤 호출을 실행하는가에 달려 있다(24장). 둘째, 행동의 품질은 \(p_1\sim p_4\)와 \(a_I\)의 곱으로 나뉘어 각 단계를 따로 측정하고 고칠 수 있다. 호출과 관찰을 되풀이하는 루프는 14장, 도구를 모델에 연결하는 표준인 MCP는 19장에서 다룬다.

도구 호출의 입력·결과

도구는 모델에게 세 가지로 보인다. 이름, 설명, 입력 스키마이다. 이 셋은 모델이 읽는 글, 곧 컨텍스트의 일부이다. Claude API 문서에 따르면 tools 파라미터(이름, 설명, 스키마)와 tool_use·tool_result 블록이 모두 입력 토큰으로 세어지고, tools를 쓰면 API가 도구 사용을 안내하는 시스템 프롬프트를 따로 붙이는데 그 길이는 모델마다 다르다(Claude Opus 5.5와 Sonnet 5.5는 tool_choice가 auto나 none일 때 286토큰이다. Tool use with Claude, 2026년 11월 확인). 이 장의 실험에서 이름 하나, 설명 한 문장, 인자 하나인 읽기 도구는 Qwen3의 대화 템플릿으로 프롬프트에 152토큰을 더했고, 쓰기 도구와 목록 도구 둘은 248토큰을 더했다(E0). 12장의 비용 모델로 세면 152토큰을 더 읽는 prefill은 Qwen3-1.7B에서 437 GFLOPs, 248토큰은 718 GFLOPs이다. 하네스는 호출할 때마다 컨텍스트를 다시 보내므로, 이 몫은 도구를 부르는 모든 턴에 든다. 같은 문서는 도구 설명을 '도구가 무엇을 하고, 언제 쓰고 쓰지 말아야 하고, 인자가 무엇을 뜻하고, 무엇을 돌려주지 않는지'까지 자세히 쓰라고 하며(도구당 최소 3~4문장), 결과에는 다음 단계를 추론하는 데 필요한 정보만 돌려주라고 한다(Define tools, 같은 시기 확인). 설명을 늘리는 일은 길이가 되어 토큰으로 돌아오고, 이는 12장이 센 비용의 같은 항이다.

인자는 어디서 오는가

모델이 낸 인자 \(a\)가 맞으려면(\(C_3\)) 값이 어디선가 와야 한다. 값의 출처는 셋이다.

인자의 출처: 복사, 유도, 추측

호출의 인자 값 \(a^*\)(맞는 값)에 대해 컨텍스트가 \(a^*\)를 글자 그대로 담고 있으면 그 인자는 복사이다(사용자가 말한 SKU, 앞 결과에 나온 ID). \(a^*\)가 컨텍스트의 값에서 정해진 규칙으로 계산되면 유도이다(날짜의 형식 변환, 두 값의 합). 컨텍스트가 \(a^*\)에 대한 정보를 담지 않으면 추측이다. 값 \(a^*\)가 후보 집합 \(D\)(\(|D|=V\))에서 균등하게 정해지는 도구를 생각한다.

인자의 상한과 관측 동일성
  1. 추측의 상한. 컨텍스트가 \(a^*\)와 독립이면 어떤 호출 정책도 \(\Pr[C_3]\le1/V\)이다.
  2. 스키마가 주는 정보. 스키마(이름과 설명 포함)가 \(a^*\)가 부분집합 \(D'\subseteq D\)에 든다고 알려 주면(예: enum) 상한은 \(1/|D'|\)로 오른다. 형식만 제한하는 스키마(타입, 자릿수 패턴)는 \(D\) 안의 후보 수를 줄이지 않으므로 \(1/V\)를 올리지 못한다.
  3. 스키마 강제. 출력을 스키마에 맞는 것으로만 제한하는 디코딩은 \(p_2=1\)을 만든다. \(p_3\)의 상한은 1, 2번 그대로이다.
  4. 복사와 유도. 복사는 상한이 없다. 정책이 컨텍스트에서 값을 옮기면 \(\Pr[C_3]\)가 1에 이를 수 있다.
  5. 관측 동일성. 두 세계 \(w,w'\)에서 하네스가 모델에게 준 컨텍스트가 글자까지 같으면 모델의 출력 분포가 같다. 따라서 두 세계의 정답 \(x_w\ne x_{w'}\)이면 정확도의 합 \(\mathrm{Acc}_w+\mathrm{Acc}_{w'}\le1\)이고, 모델이 '이상하다'고 알아채는 확률(답을 바꾸거나 되묻는 확률)도 두 세계에서 같다. 도구가 다른 레코드를 성공으로 돌려주는 세계에서, 결과가 그 레코드의 키를 싣지 않으면 두 컨텍스트는 같고, 키를 실으면 달라진다.
증명

1번: 호출의 인자 \(\hat a\)가 \(a^*\)와 독립인 입력의 함수이므로(확률적이어도 같다) \(\Pr[\hat a=a^*]=\sum_a\Pr[\hat a=a]/V\le1/V\)이다(정리 11.1의 1번과 같은 논리). 2번: 스키마가 컨텍스트에 있으므로 \(a^*\)의 사후 분포의 받침이 \(D'\)로 줄고 그 위에서 균등하다. 형식 제약은 받침을 줄이지 않는다. 3번: 제한 디코딩은 출력 집합을 스키마에 맞는 문자열로 좁히는 함수이다. 모델의 입력은 그대로여서 \(a^*\)에 대한 정보가 늘지 않고 1, 2번의 상한을 넘지 못한다. 4번: 복사하는 정책이 \(a^*\)를 정확히 옮기면 \(C_3\)가 성립한다. 5번: 세계는 컨텍스트를 통해서만 모델에 닿으므로 컨텍스트가 같으면 출력의 분포가 같다. 그러면 사건 '출력이 \(x_w\)를 말한다'와 '출력이 \(x_{w'}\)를 말한다'는 서로 소이고 같은 분포 위에 있으므로 확률의 합이 1 이하이다.

SKU 하나를 맞히는 일

SKU 코드가 SKU- 뒤에 네 자리 숫자(1000~9999)이면 \(V=9{,}000\)이다. 사용자가 코드를 말하지 않고 상품 이름만 말했는데 모델이 코드를 추측해 부르면 \(\Pr[C_3]\le1/9{,}000=0.00011\)이다. 도구의 스키마에 같은 창고의 상품 40개를 enum으로 적어 두면 \(1/40=0.025\)이고, 이름과 코드를 짝지어 적어 두면 이름에서 코드를 복사할 수 있어 상한이 없어진다. 스키마가 ^SKU-\d{4}$ 같은 형식을 강제해도 모델은 형식에 맞는 9,000개 가운데 하나를 여전히 고른다. 사용자가 입력한 코드의 한 자리가 틀렸다면(이 장의 실험의 오타 조건) 그 코드는 형식에 맞아 \(C_2\)를 통과하고 \(C_3\)에서 실패한다. 이 장의 실험은 코드가 사용자 메시지에 글자 그대로 있는 복사 조건에서 시작한다.

Claude API 문서의 strict: true는 스키마 적합을 보증한다. 문서는 문법으로 제한한 샘플링(grammar-constrained sampling)으로 도구의 input이 input_schema를 정확히 따르고 도구 이름이 항상 유효하다고 쓰며, 예로 passengers: 2 대신 "two"나 "2"가 나오는 일을 막는다고 한다(Strict tool use, 2026년 11월 확인). 이것은 \(p_2=1\)이다. 문서가 보증하는 것은 형식이고 값이 맞는지는 말하지 않으며, 의 3번이 그 구분이다. Define tools 문서는 Fable 5.2, Opus 5.5, Sonnet 5.5 등에서는 tool_choice의 any와 tool(호출을 강제하는 설정)이 400 오류를 낸다고 쓰며 대신 auto와 strict를 쓰라고 한다. 호출을 낼지(\(C_1\))는 모델이 정하고, 이 모델들에서는 하네스가 강제하지 못한다.

결과는 글이고, 같은 컨텍스트는 같은 행동을 만든다

도구의 결과는 글로 컨텍스트에 돌아온다. tool_result의 content는 문자열이나 text, image, document, search_result 블록의 목록이고, 도구가 실패했거나 호출이 무효이면 is_error: true를 단다(Handle tool calls). MCP의 도구 결과도 같은 구조이다. content 블록과 선택 항목인 structuredContent가 있고, 실행 오류는 isError: true로 알리며, 도구는 outputSchema로 결과의 모양을 약속할 수 있다(MCP 명세의 Tools, 판 2026-07-28을 2026년 11월에 확인). 어느 쪽이든 모델이 보는 것은 직렬화된 글이다.

이 사실이 의 5번으로 이어진다. 도구가 돌려준 글만이 세계와 모델을 잇는다. 도구가 버그로 다른 SKU의 레코드를 성공으로 돌려주었는데 결과가 {"stock": 781}이면, 맞는 레코드를 돌려준 세계의 컨텍스트와 글자까지 같다. 모델의 어떤 지능도 이 두 세계를 가르지 못한다. 결과가 {"sku": "SKU-9693", "stock": 781}처럼 자기 키를 실으면 요청한 키와 돌아온 키가 컨텍스트 안에서 대조 가능해진다. 대조를 모델이 하는지는 별개의 문제이다. 정보가 글에 있다는 것과 모델이 그 정보를 쓰는지는 다르다(정리 11.4의 3번 이후의 논의와 같다). 이 장의 실험(R5)이 이 두 가지를 갈라서 잰다.

1%의 조용한 오류

(가상의 값) 조회 도구가 1%의 질의에서 이웃 레코드를 성공으로 돌려주고 결과가 키를 싣지 않는다고 하자. 결과를 그대로 말하는 정책의 정확도는 0.99이다. 모델이 이상하다고 알아채는 정책을 만들어도 두 세계의 컨텍스트가 같아서 알아채는 확률이 두 세계에서 같다(의 5번). 알아챔이 늘면 정상 99%에서도 같은 비율로 거짓 경보가 늘 뿐 1%의 오류만 골라내지 못한다. 이 1%는 모델이나 프롬프트로는 줄지 않고, 도구의 출력에 키를 싣는 설계 변경으로만 드러낼 수 있다.

결과가 모델로 돌아온다는 점에는 위험도 따른다. 결과는 웹페이지, 받은 메일, 사용자 업로드, 제3자 API처럼 통제할 수 없는 곳에서 온 글일 수 있고, 거기에 지시를 심으면 모델의 행동을 바꿀 수 있다(간접 프롬프트 주입). Claude API 문서는 그런 내용을 system 프롬프트나 일반 user 텍스트가 아니라 tool_result 안에 두라고 안내한다(Handle tool calls). 도구 결과 속 지시는 24장이 다룬다.

도구 정의와 결과는 컨텍스트 예산을 쓴다

도구가 열 개, 스무 개로 늘면 정의가 매 호출 컨텍스트의 앞부분을 차지하고(위의 152토큰이 열 배가 된다), 결과가 길면 12장의 희석과 방해가 시작된다. 이 부담을 줄이는 길은 정의를 줄이거나(관련 작업을 하나의 도구로 묶기), 필요할 때만 정의를 불러오거나(Claude API의 tool search tool이 이런 방식이다), 결과를 짧게 돌려주는 것이다. 무엇을 컨텍스트에 남기고 지울지는 20장, 도구를 연결하는 표준과 정의를 불러오는 방식은 19장에서 다룬다.

실패와 재시도

도구 호출은 여러 곳에서 실패한다. 실패의 종류를 가르는 기준은 두 가지이다. 누가 실패를 알아채는가, 그리고 같은 호출을 다시 부르면 결과가 달라지는가이다.

무효한 호출하네스(스키마 검사)필수 인자가 없음, 타입이 다름같은 오류. 인자를 고쳐야 한다

앞의 셋은 오류 결과의 글로 컨텍스트에 돌아온다. Claude API에서는 도구가 실패했거나 호출이 무효이면 tool_result에 is_error: true를 달아 돌려보내며, 문서는 그러면 Claude가 같은 도구를 새 tool_use로 다시 부를 수 있으므로 하네스의 루프가 허용하는 재시도 횟수를 제한하라고 쓴다. 또 '실패했다'만 적지 말고 무엇이 잘못되었고 다음에 무엇을 시도해야 하는지를 적으라고 한다(예: 'Rate limit exceeded. Retry after 60 seconds.'. Handle tool calls, 2026년 11월 확인). MCP 명세도 같은 구분을 둔다. 입력 검증 오류, API 실패, 업무 규칙 위반 같은 실행 오류는 모델이 보고 고쳐서 다시 시도할 수 있는 피드백이므로 isError: true로 결과에 담아 모델에 주라고 하고, 알 수 없는 도구나 깨진 요청 같은 프로토콜 오류는 모델이 고칠 가능성이 낮다고 쓴다(MCP 명세의 Tools). 도구가 돌려주는 오류는 모델 바깥에서 오는 신호이다. 7장이 인용한 Huang 외는 외부 피드백 없이 모델이 자기 추론을 고치게 했을 때 성능이 오르지 못하고 떨어질 수 있다고 보고했고, Gou 외(CRITIC)는 도구와 상호작용해 얻은 피드백으로 모델이 자기 출력을 검증하고 고치게 하면 질의응답, 수학 프로그램 합성, 독성 줄이기에서 성능이 고르게 오른다고 보고하며 외부 피드백이 중요하다고 주장한다(초록). 둘 다 그들이 시험한 모델과 과제에 한정된 자료의 주장이다.

그러면 오류를 본 모델이 다시 부르는 일은 언제 도움이 되는가. 이것은 모델의 성향이기 전에 실패의 구조가 정한다.

재시도가 도움이 되는 조건

한 호출의 일시 실패는 호출마다 독립이고 확률 \(q\)라 하자. 영구 실패는 같은 인자에 대해 항상 같은 오류를 낸다. 정책은 같은 호출을 최대 \(r\)번 다시 부른다(\(r+1\)번까지 시도한다).

  1. 영구 실패는 되풀이로 풀리지 않는다. 같은 인자로 \(r\)번 되풀이해도 성공 확률은 0이고, 컨텍스트에는 (호출, 오류) 쌍이 \(r\)번 더 쌓인다.
  2. 일시 실패. 성공 확률은 \(1-q^{r+1}\), 기대 호출 수는 \(\dfrac{1-q^{r+1}}{1-q}\), \(r+1\)번 모두 실패할 확률은 \(q^{r+1}\)이다.
  3. 종류를 알리지 않는 오류. 호출이 영구 실패인 비율이 \(\rho\), 나머지가 일시 실패 \(q\)이고 첫 오류의 글이 두 종류에서 같다고 하자. 모델은 첫 오류 뒤에 두 종류에서 같은 행동을 하며(의 5번), 같은 인자로 \(r\)번 되풀이하는 정책의 성공 확률은 \((1-\rho)(1-q^{r+1})\)이어서 \(r\to\infty\)에서도 \(1-\rho\)를 넘지 못한다. 기대 호출 수는 \((1-\rho)\dfrac{1-q^{r+1}}{1-q}+\rho(r+1)\)이다. 오류가 종류를 알리고(예: retryable) 정책이 그에 따라 일시 실패에서만 다시 부르면 성공 확률은 같고 기대 호출 수는 \((1-\rho)\dfrac{1-q^{r+1}}{1-q}+\rho\)이다. 영구 실패에서 \(\rho r\)번의 호출을 아낀다.
  4. 틀린 인자와 오류가 주는 정보. 오류의 원인이 틀린 인자이고 맞는 인자가 \(N\)개의 후보에서 균등하며 오류가 후보에 대한 정보를 주지 않으면(예: not_found), 서로 다른 \(r\)개를 시도하는 어떤 정책의 성공 확률도 \(r/N\) 이하이다. 오류가 맞는 인자를 알려 주면(예: did_you_mean) 값을 옮기는 한 번의 재시도로 성공할 수 있다.
증명

1번: 도구가 결정적이므로 \(r\)번 모두 같은 오류이고, 성공하는 호출이 없다. 2번: \(j\)번째 시도가 일어나는 것은 앞의 \(j-1\)번이 모두 실패했을 때이므로 확률이 \(q^{j-1}\)이다. 기대 호출 수는 \(\sum_{j=1}^{r+1}q^{j-1}=(1-q^{r+1})/(1-q)\)이다. 모두 실패할 확률은 \(q^{r+1}\)이고 그 여사건이 성공이다. 3번: 영구 실패인 호출은 \(r+1\)번 모두 실패하여 호출이 \(r+1\)개이고, 일시 실패인 호출에는 2번의 식이 적용된다. 확률 \(\rho\)와 \(1-\rho\)로 평균한다. 종류를 알면 영구 실패는 첫 오류에서 멈추므로 호출이 1개이다. 첫 오류가 같으면 모델의 다음 행동이 같다는 것은 의 5번이다. 4번: 각 호출은 후보 하나가 맞는지 시험할 뿐이고, 틀리면 그 후보를 지울 뿐이다. 후보가 균등하므로 서로 다른 \(r\)개 가운데 정답이 있을 확률은 \(r/N\)이다. 알려 주는 오류는 후보를 하나로 줄인다.

재시도의 값과 낭비

일시 실패가 \(q=0.3\)인 도구를 최대 3번 다시 부르면(\(r=3\)) 성공 확률은 \(1-0.3^4=0.9919\)이고 기대 호출 수는 1.417이다. 재시도 없이는 0.7이다. 이제 호출의 30%가 영구 실패(\(\rho=0.3\))이고 첫 오류가 종류를 알리지 않는다고 하자. 같은 호출을 3번 다시 부르는 정책의 성공 확률은 \(0.7\times0.9919=0.694\)이고 \(r\)을 아무리 늘려도 0.7을 넘지 못한다. 기대 호출 수는 2.192이다. 오류가 종류를 알려 영구 실패에서 다시 부르지 않으면 성공 확률은 같고 호출 수가 1.292로 \(\rho r=0.9\)번 준다. 성공 확률이 같은데 호출이 41% 적다(E0이 센 값). 오타 키의 경우(이 장의 실험의 R3) 맞는 키가 입력한 키에서 뒤 세 자리 중 하나를 바꾼 \(N=27\)개 후보에서 균등하면, 호출 한도 4번 가운데 첫 호출이 오타 키이고 나머지 3번이 서로 다른 후보를 시도하는 최선의 정책이 맞히는 확률은 \(3/27=0.111\)이다. 오류가 맞는 키를 알려 주면 한 번의 재시도로 1에 이른다.

정리의 3번은 재시도의 위치에 대해 말한다. 일시 실패인지 영구 실패인지는 도구와 하네스가 안다. HTTP 503과 404를 구분하는 곳은 도구이고, 모델은 두 오류가 글자까지 같게 오면 구분할 수 없다. 그러므로 종류를 알 수 있는 일시 실패는 하네스가 모델 모르게 되풀이하는 편이(제한된 횟수, 대기 시간을 두고) 토큰도 아끼고 모델의 순응에 기대지도 않는다. 모델에게 보여 줄 오류는 판단이 필요한 것, 곧 인자를 바꿔야 하거나 포기해야 하는 것이다. 이때 4번이 설계의 기준을 준다. 오류 메시지는 정보의 통로이다. 'not found'는 후보 하나를 지우는 정도의 정보를 주고, 맞는 키를 말해 주는 메시지는 \(\log_2N\)비트를 준다. 다만 도구가 알려 주는 '맞는 키'가 사용자가 뜻한 키가 맞는지는 별개이다. 자동 교정은 사용자가 말한 것과 다른 레코드로 조용히 갈아타는 일이어서, 교정했다는 사실을 사용자에게 알리는 것까지가 설계이다.

재시도 한도는 하네스의 정책이다

Claude API 문서가 루프의 재시도 횟수를 제한하라고 한 것은 위의 정리의 3번 때문이다. 한도가 없으면 영구 실패에서 호출과 오류가 컨텍스트에 쌓이며 비용이 늘고(정리 12.1), 한도가 너무 낮으면 일시 실패에서 정답을 놓친다. 한 작업 안에서 에이전트가 언제 멈추는지는 15장, 여러 시도와 세션에 걸친 바깥 루프의 종료는 30장이 다룬다.

읽기 도구와 쓰기 도구

지금까지의 도구는 읽기였다. 읽기를 다시 부르면 컨텍스트가 길어질 뿐 세계는 그대로이다. 쓰기는 다르다. 다시 부르면 세계가 다시 바뀔 수 있다. 이 구분은 새로운 것이 아니다. HTTP의 의미 규칙(RFC 9110, 9.2절)이 같은 구분을 정의한다. 메서드는 의미가 본질적으로 읽기 전용이어서 클라이언트가 서버의 상태 변화를 요청하지도 기대하지도 않으면 안전(safe)하다. 같은 메서드로 보낸 여러 번의 똑같은 요청의 의도된 효과가 한 번 보낸 것과 같으면 멱등(idempotent)하다. 문서는 멱등한 메서드를 따로 가르는 이유를, 응답을 읽기 전에 통신이 끊기면 요청을 자동으로 다시 보낼 수 있기 때문이라고 쓰고, 멱등하지 않은 요청은 의미가 사실상 멱등임을 아는 방법이나 원래 요청이 적용되지 않았음을 확인하는 방법이 없으면 자동으로 재시도하지 말아야 한다고 쓴다(RFC 9110의 9.2.1, 9.2.2). 도구 호출은 HTTP가 아니지만, 응답이 오지 않았을 때 요청이 적용되었는지 모른다는 구조는 같다.

도구의 부작용 분류

도구를 효과에 따라 셋으로 나눈다. 읽기 전용은 세계를 바꾸지 않는다. 멱등 쓰기는 같은 인자로 여러 번 불러도 효과가 한 번 부른 것과 같다(예: 상태를 'shipped'로 설정). 비멱등 쓰기는 부를 때마다 효과가 쌓인다(예: 재고를 25개 예약, 메일 보내기). 파괴적인지(되돌릴 수 없는지)는 별개의 축이다. 이 분류는 도구를 만든 쪽이 붙이는 표시이고, 도구의 실제 동작과 다를 수 있다.

MCP는 이 표시를 도구 정의에 싣는 자리를 둔다. annotations의 readOnlyHint(참이면 환경을 바꾸지 않음, 기본값 거짓), destructiveHint(참이면 파괴적 갱신을 할 수 있음, 기본값 참), idempotentHint(참이면 같은 인자로 되풀이해도 추가 효과가 없음, 기본값 거짓), openWorldHint(외부 개체와 상호작용할 수 있음)이다. 명세는 이 속성이 모두 힌트이며 도구의 동작을 충실하게 기술한다는 보장이 없고, 클라이언트는 신뢰할 수 없는 서버가 준 주석으로 도구 사용을 결정하면 안 된다고 쓴다(MCP 명세의 Tools와 스키마의 ToolAnnotations, 판 2026-07-28, 2026년 11월 확인). 기본값이 가장 보수적인 쪽(쓰기이고 파괴적이고 멱등하지 않음)이라는 점이 눈에 띈다. 아무 표시도 없는 도구는 가장 위험한 도구로 다뤄야 한다. 이 표시를 근거로 실행을 허용하고 확인하고 거부하는 규칙은 24장이 다룬다.

이제 쓰기 도구의 응답이 사라졌을 때를 생각하자. 호출이 서버에 닿지 못할 확률이 \(u\), 닿으면 효과가 한 번 일어나고 그 응답이 유실될 확률이 \(v\)라 하자(호출마다 독립). 하네스가 보는 타임아웃의 확률은 \(q=u+(1-u)v\)이다.

응답이 유실된 쓰기는 어느 쪽으로든 틀린다
  1. 타임아웃은 모호하다. 타임아웃의 컨텍스트는 효과가 있었든 없었든 같으므로(의 5번) 모델의 다음 행동이 같다. 타임아웃일 때 효과가 있었을 확률은 \(\theta=(1-u)v/q\)이다. 다시 부르면 확률 \(\theta\)로 중복이 생긴다. 다시 부르지 않고 실패를 보고하면 확률 \(1-\theta\)로 효과 없이 일이 끝나고, 확률 \(\theta\)로는 효과가 있는데도 실패라고 말한 것이 된다.
  2. 비멱등 쓰기의 중복. 타임아웃마다 최대 \(r\)번 다시 부르면 효과의 횟수 \(K\)의 기댓값은 \(\mathbb E[K]=(1-u)\dfrac{1-q^{r+1}}{1-q}\)이다. 응답만 유실되는 경우(\(u=0\), \(q=v\))에는 \(K\)가 호출 수와 같고 \(\Pr[K\ge2]=q\), 기대 중복은 \(\sum_{k=1}^{r}q^k\)이다.
  3. 멱등 키. 호출이 같은 멱등 키를 싣고 서버가 같은 키의 요청을 걸러내면 \(r\)과 무관하게 최종 효과는 최대 1번이다. 호출 수의 분포는 2번과 같다. 키를 매번 새로 지으면 같은 요청이 아니므로 이 보장이 없다.
  4. 확인 후 재시도. 신뢰할 수 있는 읽기로 효과의 유무를 확인한 뒤에만 다시 부르면 효과는 최대 1번이고, 타임아웃마다 읽기 호출 1번이 더 든다.
증명

1번: 타임아웃은 '닿지 못함'(확률 \(u\)) 또는 '닿았으나 응답 유실'(확률 \((1-u)v\))이고, 조건부 확률이 \(\theta\)이다. 두 경우에서 하네스가 모델에 돌려주는 글이 같으므로 행동이 같고, 행동이 '다시 부름'이면 효과가 이미 있는 세계에서 하나가 더해진다. 2번: \(j\)번째 시도가 일어나는 확률은 앞 시도가 모두 타임아웃인 \(q^{j-1}\)이고 시도가 일어나면 그 시도가 효과를 낼 확률은 \(1-u\)이다(그 시도의 결과는 앞 시도들과 독립이다). 합하면 \((1-u)\sum_{j=1}^{r+1}q^{j-1}\)이다. \(u=0\)이면 \(K\)가 시도 수이고 \(\Pr[K\ge2]\)는 첫 시도가 타임아웃일 확률 \(q\)이다. 기대 중복은 \(\mathbb E[K]-1=\sum_{k=1}^{r}q^k\)이다. 3번: 서버가 같은 키를 한 번만 적용하면 효과는 최소 1번이 닿은 뒤로 1번에서 멈춘다. 4번: 재시도 전에 효과가 없다고 확인되면 그 시도가 처음 적용이 된다.

재시도가 만드는 중복

호출은 항상 서버에 닿고(\(u=0\)) 응답이 \(q=0.3\)의 확률로 유실되는 예약 도구를 타임아웃마다 최대 3번 다시 부르면 효과의 기댓값은 1.417번, 요청 하나당 기대 중복이 0.417번이다. 첫 시도에서 타임아웃이 난 30%의 요청에서 중복이 시작된다. 4번 시도하고도 응답을 못 받는 확률은 \(0.3^4=0.0081\)이고, 그때 효과는 4번 적용되어 있다. 멱등 키를 쓰면 같은 시도 수에서 최종 효과가 1번이다. 호출이 닿지 못할 확률이 \(u=0.1\), 응답이 유실될 확률이 \(v=0.2\)이면 \(q=0.28\)이고, 타임아웃일 때 효과가 있었을 확률은 \(\theta=0.18/0.28=0.643\)이다. 다시 부르면 64%의 확률로 중복이고, 부르지 않으면 36%의 확률로 효과가 없다. 어느 쪽으로든 틀릴 확률이 크고, 모델이 줄일 수 있는 것은 아니다. 줄이려면 컨텍스트에 정보가 더 들어와야 한다. 효과의 유무를 읽는 도구, 멱등 키, 또는 오류 메시지에 '처리되었을 수 있다'는 사실을 적는 것이다.

표의 세 번째 열은 모델에게 맡길 수 있는 판단이 아니다. 정리의 1번이 말하듯 타임아웃을 본 모델은 두 세계를 구별할 수 없기 때문이다. 다시 부를지 말지를 모델의 성향에 맡기면 \(\theta\)와 모델의 재시도 습관이 곱해진 결과를 받게 된다. 이 장의 실험은 같은 타임아웃에 오류 메시지의 글만 바꿔서(아무 말 없음, '재시도 가능', '처리되었을 수 있으니 먼저 확인하라') 모델이 얼마나 다르게 반응하는지 잰다.

표시는 허용·확인·거부 규칙의 입력이다

에이전트 하네스는 도구마다 읽기, 쓰기, 파괴적 쓰기를 구분해 읽기는 자동으로 허용하고 쓰기는 확인을 받고 파괴적 쓰기는 거부하는 식의 규칙을 둔다. 이 규칙이 믿는 표시는 도구를 만든 쪽의 주장이다. MCP 명세가 주석을 힌트로만 다루고 신뢰할 수 없는 서버의 주석에 기대지 말라고 하는 이유가 이것이다. 자신이 만든 도구의 표시는 신뢰하고 외부 서버의 도구는 쓰기로 가정하는 것이 안전한 기본값이라는 것이 이 책의 권고이다. 규칙과 신뢰 경계는 24장, 외부 서버의 도구를 연결하는 방법은 19장에서 다룬다.

실험: 도구가 오류를 돌려줄 때 모델은 어떻게 반응하는가

슬롯에 적어 둔 질문은 '작은 조회 도구가 오류를 돌려줄 때 모델은 어떻게 반응하는가'였다. 11장, 12장처럼 모델 없이 이 장의 계산을 먼저 확인하고(E0), 작은 언어모델에게 가상의 창고 도구를 주어 도구의 응답을 바꿔 가며 반응을 잰다(E1~E6). 반응은 다시 부르는지, 인자를 고치는지, 값을 지어내는지, 사용자에게 돌려주는지, 쓰기를 겹치게 하는지이다. 세계는 가상의 창고이다. SKU 코드(SKU- 뒤의 네 자리)와 재고(100~999)는 균등한 무작위 값이어서 모델이 가중치로 알 수 없고, 정답과 도구가 무엇을 돌려주는지를 코드가 안다. 그래서 답을 기계로 채점할 수 있고, 정답이 도구 결과에 나타나지 않은 시행에서 정답을 말하는 비율의 상한이 이론으로 정해진다(). 이 실험이 보여 주는 것은 이 두 모델과 이 도구에서의 행동이지 도구 사용 일반이나 Claude의 성질이 아니다. def ci(x, rr):                                                 # 시행 단위 부트스트랩 95% 구간
    x = np.asarray(x, float); b = x[rr.integers(0, len(x), (BOOT, len(x)))].mean(1)
    return float(x.mean()), float(np.percentile(b, 2.5)), float(np.percentile(b, 97.5))


# ---------- E0: 모델 없이 확인하는 계산 (정리 13.3, 13.4) ----------
def retry_loop(rr, q, r, n=200000):                            # 응답이 확률 q로 실패(독립)하는 호출을 최대 r번 다시 부른다
    fail = rr.random((n, r + 1)) < q; lead = np.cumprod(fail, axis=1).sum(1)   # 앞에서부터 연속으로 실패한 횟수
    return dict(success=float((lead <= r).mean()), calls=float(np.minimum(lead + 1, r + 1).mean()),
                formula_success=1 - q ** (r + 1), formula_calls=(1 - q ** (r + 1)) / (1 - q), unknown=float((lead == r + 1).mean()), formula_unknown=q ** (r + 1))


def candidates(typed):                                         # 입력한 키에서 뒤 세 자리 중 하나만 다른 키(첫 자리는 같다)
    return [f"SKU-{k}" for k in range(1000, 10000) if f"SKU-{k}" != typed and typed[4] == str(k)[0] and sum(a != b for a, b in zip(typed[5:], str(k)[1:])) == 1]


def guess_policy(rr, r, n=100000):                             # 후보 27개에서 정답이 균등할 때 서로 다른 r개를 시도하는 정책의 성공률
    truth = rr.integers(0, N_CAND, n); order = np.argsort(rr.random((n, N_CAND)), axis=1)[:, :r]
    return float((order == truth[:, None]).any(1).mean())


def mixed_policy(q, rho, r):                                   # 영구 실패 비율 rho, 나머지는 일시 실패 q: 같은 인자로 r번 다시 부를 때(정리 13.3의 3번)
    ok = (1 - rho) * (1 - q ** (r + 1)); calls_always = (1 - rho) * (1 - q ** (r + 1)) / (1 - q) + rho * (r + 1); calls_label = (1 - rho) * (1 - q ** (r + 1)) / (1 - q) + rho
    return dict(success=ok, calls_always=calls_always, calls_label=calls_label, saved=calls_always - calls_label)


def e0_pure():
    rr = np.random.default_rng(SEED); res = {}
    res["retry"] = {f"{q}|{r}": retry_loop(rr, q, r) for q in (0.1, 0.3, 0.5) for r in (0, 1, 2, 3)}
    res["cand"] = [len(candidates(s)) for s in ("SKU-4127", "SKU-9031", "SKU-1999", "SKU-7000")]
    res["guess"] = {r: guess_policy(rr, r) for r in (1, 2, 3, 4)}
    res["mixed"] = {f"{rho}|{r}": mixed_policy(0.3, rho, r) for rho in (0.1, 0.3) for r in (1, 3)}
    return res


def e0_tokens(tok):                                            # 도구 정의가 프롬프트에 더하는 토큰과 prefill FLOPs (12장의 공식)
    d, dk, df = DIM["d"], DIM["d_kv"], DIM["d_ff"]; c = 4 * d * d + 4 * d * dk + 6 * d * df; res = {}
    msgs = [{"role": "system", "content": S1}, {"role": "user", "content": ASK[0].format(sku="SKU-4172")}]
    for k, tools in (("get", TOOLS_R), ("write", TOOLS_W)):

        b = len(tok(tok.apply_chat_template(msgs, add_generation_prompt=True, tokenize=False, enable_thinking=False)).input_ids)
        fl = lambda n: DIM["L"] * (n * c + 4 * n * n * d)
        res[k] = dict(with_tools=a, without=b, extra=a - b, extra_gflops=(fl(a) - fl(b)) / 1e9, c=c)
    return res

def world(t):                                                  # 시행 t의 세계. 같은 t는 모든 조건에서 같다
    r = np.random.default_rng([SEED, t]); sku = f"SKU-{r.integers(1000, 10000)}"; stock = int(r.integers(100, 1000))

    def tweak(s):                                              # 뒤 세 자리 중 한 자리를 다른 숫자로 바꾼다
        p = 4 + 1 + int(r.integers(3)); return s[:p] + str(r.choice([c for c in "0123456789" if c != s[p]])) + s[p + 1:]
    other_stock = int(r.integers(100, 1000))
    while other_stock == stock: other_stock = int(r.integers(100, 1000))
    return dict(sku=sku, stock=stock, typo=tweak(sku), other=tweak(sku), other_stock=other_stock, phr=int(r.integers(3)), qty=int(r.integers(5, 60)), order=ORDERS[int(r.integers(3))])


def check(name, args):                                         # 스키마 검사: 틀리면 오류 문자열
    sp = SPEC.get(name)
    if sp is None: return "unknown tool"
    if not isinstance(args, dict): return "arguments must be an object"
    for k in sp["required"]:
        if k not in args: return f"missing required argument: {k}"
    for k, v in args.items():
        if k not in sp["properties"]: return f"unexpected argument: {k}"
        ty = sp["properties"][k]["type"]
        if (ty == "string" and not isinstance(v, str)) or (ty == "integer" and (not isinstance(v, int) or isinstance(v, bool))): return f"wrong type for argument: {k}"
    return None


def execute(arm, w, st, name, args):                           # 도구 하나를 실행해 결과(dict)를 돌려준다. st는 시행 안의 상태
    bad = check(name, args)
    if bad: return {"error": "invalid_arguments", "detail": bad}
    if name == "get_stock":
        st["gets"] += 1
        if arm == "R1" or (arm == "R2" and st["gets"] == 1): return {"error": "service_unavailable"}                      # 영구/일시 실패. 첫 오류는 두 조건에서 글자까지 같다
        if arm == "R1L": return {"error": "forbidden", "retryable": False}                                              # 같은 실패에 클래스 라벨을 붙인다
        if arm == "R2L" and st["gets"] == 1: return {"error": "timeout", "retryable": True}
        if arm == "R5a": return {"stock": w["other_stock"]}                        # 도구의 결함: 다른 SKU의 레코드를 돌려준다(키를 싣지 않음)
        if arm == "R5b": return {"sku": w["other"], "stock": w["other_stock"]}     # 같은 결함, 레코드가 자기 키를 싣는다
        if args["sku"] == w["sku"]: return {"sku": w["sku"], "stock": w["stock"]}
        if arm == "R4": return {"error": "not_found", "did_you_mean": w["sku"]}                                         # 정보: 맞는 키를 알려 준다
        if arm == "R4i": return {"error": "not_found", "suggestion": f"Retry get_stock with sku {w['sku']}."}           # 같은 정보를 다음 행동의 지시로 쓴다
        return {"error": "not_found"}
    if name == "reserve_units":                                # 효과는 요청이 닿으면 일어난다. 첫 응답은 유실된다
        st["applied"].append(dict(id=f"R-{len(st['applied']) + 1:03d}", sku=args["sku"], qty=args["qty"]))
        if len(st["applied"]) == 1: return {"error": "timeout", **({"note": NOTE} if arm == "W1b" else {"retryable": True} if arm == "W1c" else {})}
        return {"status": "reserved", "reservation_id": st["applied"][-1]["id"]}
    return {"sku": args["sku"], "reservations": [dict(id=x["id"], qty=x["qty"]) for x in st["applied"] if x["sku"] == args["sku"]]}


def parse_calls(text):                                         # <tool_call> 블록을 읽는다. (호출 목록, 형식이 깨졌는가)
    if "<tool_call>" not in text: return [], False
    calls = []
    for m in re.findall(r"<tool_call>\s*(.*?)\s*</tool_call>", text, re.S):
        try: c = json.loads(m)
        except ValueError: return [], True
        if not isinstance(c, dict) or not isinstance(c.get("name"), str): return [], True
        calls.append(dict(name=c["name"], arguments=c.get("arguments")))
    return (calls, False) if calls else ([], True)


def trial(answer, arm, prompt, t):
    w, write = world(t), arm.startswith("W"); typed = w["typo"] if arm in ("R3", "R4", "R4i") else w["sku"]
    user = (RES if write else ASK)[w["phr"]].format(sku=typed, qty=w["qty"], order=w["order"])
    msgs = [{"role": "system", "content": SYSP[prompt]}, {"role": "user", "content": user}]; tools = TOOLS_W if write else TOOLS_R
    st, log, texts, tokens, status = dict(gets=0, applied=[]), [], [], 0, "ok"
    while True:
        text, n = answer(msgs, tools); tokens += n; texts.append(text); calls, bad = parse_calls(text)
        if bad: status, final = "malformed", text; break
        if not calls: final = text; break
        if len(log) >= MAXCALL: status, final = "unfinished", text; break           # 호출 한도에 이르렀는데도 또 부른다
        calls = calls[:MAXCALL - len(log)]
        msgs.append({"role": "assistant", "content": text.split("<tool_call>")[0].strip(), "tool_calls": [{"type": "function", "function": c} for c in calls]})
        for c in calls:
            res = execute(arm, w, st, c["name"], c["arguments"]); log.append(dict(name=c["name"], args=c["arguments"], res=res)); msgs.append({"role": "tool", "content": json.dumps(res)})
    keys = [(c["name"], json.dumps(c["args"], sort_keys=True)) for c in log]
    rec = dict(arm=arm, prompt=prompt, t=t, user=user, calls=log, texts=texts, final=final.strip(), status=status, tokens=tokens, n_calls=len(log),
               same=len(keys) != len(set(keys)), changed=any(k != keys[0] for k in keys[1:]), retried=len(log) >= 2)
    if write:
        names = [c["name"] for c in log]; idx = [i for i, n in enumerate(names) if n == "reserve_units"]
        rec.update(applied=len(st["applied"]), reserve_calls=len(idx), list_calls=names.count("list_reservations"),
                   checked=any(n == "list_reservations" for n in names[idx[0] + 1:]) if idx else False,
                   says_failed=bool(re.search(r"unable|fail|could not|couldn't|error|time(?:d)? ?out|not (?:be )?(?:reserved|processed|successful)", rec["final"], re.I)), says_success=bool(re.search(r"success", rec["final"], re.I)))
        return rec
    seen = {c["res"]["stock"] for c in log if "stock" in c["res"]}
    nums = {int(m) for m in re.findall(r"(?<![\w-])\d+(?![\w-])", re.sub(r"SKU-\d+", "", final))} | ({0} if re.search(r"\b(?:zero|out of stock|no units)\b", final, re.I) else set())   # 답이 말하는 수량
    cat = status if status != "ok" else "correct" if w["stock"] in nums else "wrong_record" if nums & seen else "fabricated" if nums else "none"
    rec.update(cat=cat, grounded=w["stock"] in seen, first_ok=bool(log) and log[0]["name"] == "get_stock" and isinstance(log[0]["args"], dict) and log[0]["args"].get("sku") == typed,
               hint_used=arm in ("R4", "R4i") and any(isinstance(c["args"], dict) and c["args"].get("sku") == w["sku"] for c in log[1:]),
               mentions=typed != w["sku"] and w["sku"] in final,
               noticed=arm == "R5b" and (w["other"] in final or bool(re.search(r"mismatch|different|does not match|doesn't match|not the same|instead", final, re.I))))
    return rec

def load():

    @torch.no_grad()

        cache = DynamicCache()

def summarize(recs, rr):
    a = recs[0]["arm"]; f = lambda k: ci([k(r) for r in recs], rr)
    s = dict(n=len(recs), calls=float(np.mean([r["n_calls"] for r in recs])), tokens=float(np.mean([r["tokens"] for r in recs])), retried=f(lambda r: r["retried"]),
             same=f(lambda r: r["same"]), changed=f(lambda r: r["changed"]), unfinished=int(sum(r["status"] != "ok" for r in recs)))
    if a.startswith("W"):
        s.update(once=f(lambda r: r["applied"] == 1), dup=f(lambda r: r["applied"] >= 2), applied=float(np.mean([r["applied"] for r in recs])), reserve_calls=float(np.mean([r["reserve_calls"] for r in recs])),
                 checked=f(lambda r: r["checked"]), says_failed=f(lambda r: r["says_failed"]), says_success=f(lambda r: r["says_success"]), applied_dist=dict(Counter(r["applied"] for r in recs)),
                 acct_violations=int(sum(r["applied"] != r["reserve_calls"] for r in recs)))
    else:
        s.update({c: f(lambda r, c=c: r["cat"] == c) for c in ("correct", "wrong_record", "fabricated", "none")}, other=f(lambda r: r["cat"] in ("malformed", "unfinished")),
                 grounded=f(lambda r: r["grounded"]), first_ok=f(lambda r: r["first_ok"]), hint_used=f(lambda r: r["hint_used"]), mentions=f(lambda r: r["mentions"]), noticed=f(lambda r: r["noticed"]),
                 lucky=int(sum(r["cat"] == "correct" and not r["grounded"] for r in recs)), cats=dict(Counter(r["cat"] for r in recs)))
    return s

기본 프롬프트에서 오류를 본 모델은 다시 부르지 않았다. S1의 읽기 조건 R1~R5b에서 호출은 모든 시행에서 1번이었다(재시도 0/60). 영구 실패(R1), 일시 실패(R2), 오타 키(R3), 맞는 키를 말해 주는 오류(R4)에서 모두 같았다. 재시도 지시를 더한 S3에서도 R1, R2, R1L, R3, R4는 0/60이었다. 재시도가 생긴 조건은 둘이다. R2L|S3(오류에 retryable: true를 단 일시 실패)에서 17/60(0.283 [0.167, 0.400])이 같은 인자로 다시 불러 모두 성공 결과를 받고 정답을 말했다. R4i|S3(맞는 키를 명령형으로 말해 주는 오류)에서 8/60(0.133 [0.050, 0.233])이 맞는 키로 고쳐 불러 모두 정답을 말했다. 이 두 조건에서 깔때기로 읽으면 정확도는 \(\Pr[I]\cdot a_I\)이고(R2L|S3에서 \(0.283\times1.000\), R4i|S3에서 \(0.133\times1.000\)), 읽기 오류는 0이며 오류의 전부가 재시도를 하느냐에서 나온다. 같은 세계끼리 짝지어 견주면 R4i가 R4보다 재시도가 0.133 [0.050, 0.217] 많았고, R2L이 R2보다 0.283 [0.167, 0.400] 많았다.

모델이 다시 하겠다고 말하고 호출하지 않는 일이 흔했다. 답에 '다시 해 보겠다'류의 문장(let me try again 등)이 있는데 호출이 늘지 않은 시행이 R2L|S1 18/60, R2L|S3 16/60, R4i|S3 22/60이었다(아래 사후 분석, 낱말 판정). 하네스가 모델의 텍스트가 아니라 호출만 실행하면 사용자는 '다시 해 보겠다'는 말을 듣고 아무 일도 일어나지 않는 것을 보게 된다. 맞는 키를 알려 주는 정보는 사용자에게는 전해졌다. 답에 맞는 키가 들어간 비율이 R4|S1에서 0.72, R4|S3에서 0.80, R4i|S1에서 1.00이었다. 정보는 모델의 글을 거쳐 사용자에게 갔고 도구에는 가지 않았다.

모델이 지어낸 수량은 모두 0이었다. 지어낸 수(fabricated)는 R1, R2, R3, R4, R4i의 어느 조건에서도 0/60이었다. R2L|S1에서는 42/60(0.700 [0.583, 0.817]), R1L|S3에서 19/60(0.317 [0.200, 0.433]), R2L|S3에서 27/60(0.450 [0.317, 0.583])이었다. 이 88개에 R5b의 2개를 더한 지어낸 답 90개가 말한 수는 모두 0이었다('The stock level … is 0.'). 재고는 100~999에서 뽑았으므로 0은 어떤 시행에서도 맞을 수 없다. 도구 결과에 없는 수를 말하는 지어낸 답이 \(1/V\)이하로만 맞는다는 의 3번의 사례이다. 이 값 0은 그럴듯하다. 재고가 없다는 말은 '조회가 실패했다'는 말과 달리 사용자가 믿고 행동할 수 있다. 같은 세계끼리 짝지은 차이는 R2L|S1이 R2|S1보다 지어낸 수가 0.700 [0.583, 0.800] 많았다. 그러나 이 차이를 retryable 라벨의 효과라고 할 수는 없다. R2L은 오류의 이름도 service_unavailable에서 timeout으로 바꾸었고(R1L은 forbidden) 라벨과 이름을 따로 바꾼 조건은 없다. 이 장의 실험이 말할 수 있는 것은 오류의 글을 바꾸면 모델이 값을 지어내는 비율이 0에서 0.7까지 달라졌다는 것까지이다.

조용한 오류는 키를 실어도 모델이 잡지 못했다. 도구가 다른 SKU의 레코드를 성공으로 돌려준 R5a(키 없음)에서 60/60이 그 레코드의 수를 요청한 SKU의 재고로 말했다. 레코드가 자기 키를 싣는 R5b에서도 58/60이 같은 일을 했고 2/60은 '요청한 SKU의 재고가 0이다'라고 말했다(돌려받은 레코드의 수도 아니고 도구 결과에 없는 수이다). 호출이 늘어난 시행은 0개였고 불일치를 지적하는 낱말(different, mismatch 등)을 쓴 답도 0개였다. 낱말 판정이 '알아챘다'고 센 6/60은 모두 답에서 돌아온 키를 그대로 말한 경우였다(예: 'The current stock of SKU-1162 is 304 units.'. 요청한 키는 SKU-1166이었다). 그 답은 돌아온 레코드에 대해서는 맞고 사용자에게는 키가 바뀌었음이 보이지만, 모델이 불일치를 알아채 말한 것은 아니다. 키 반향은 두 컨텍스트를 구별 가능하게 만들지만(의 5번), 이 모델은 그 구별을 쓰지 않았다. Qwen3로도 프로브와 스모크(시드 99)를 돌려 쓰기에서 retryable: true가 중복을 만들고 확인 메모가 확인을 부르는 것, 타임아웃 뒤에 재고를 0으로 지어내는 답이 있는 것을 보았다. (3) 스모크 뒤에 바꾼 것: 모델, 조건(R1L, R2L, R4i, W1c, 재시도 지시 프롬프트 S3 추가), 채점(수량을 3자리 수에서 모든 정수와 '품절' 표현으로 넓힘. 쓰기 보고의 낱말 판정 추가), 시행 수(100에서 60). 프롬프트의 기본 문구와 도구 정의, 세계의 생성 규칙, 호출 한도는 스모크 때와 같다. (4) 사후 분석(post13.py)은 응답을 본 뒤에 썼다. R5b의 '알아챘다' 판정이 돌려받은 키를 적은 것임은 응답을 읽고서 알았고, '다시 해 보겠다고 말하고 호출하지 않음'은 응답을 읽고서 세기 시작했다. 질문(R2L의 지어낸 수와 이름·라벨의 혼재, W1c의 S1·S3 차이)도 응답을 읽고서 해석한 것이다. (5) 사전에 적은 예상의 번호 일부는 본문에서 바뀌었다. 예상 파일의 '보조정리(관측 동일성)'는 본문에서 의 5번이다. (6) 전체 실행은 두 번 했고 둘 사이에 코드와 설정을 바꾸지 않았다. 두 번째 실행은 결과 파일이 같은지 보려는 것이었고, 본문의 수는 첫 실행의 파일에서 옮겼다(두 파일이 바이트 단위로 같아서 어느 쪽에서 옮겨도 같다).
  • 이 실험이 보여 주지 못하는 것. 모델은 Qwen3-1.7B(비사고 모드)와 Qwen2.5-1.5B-Instruct 둘이고 탐욕 디코딩 하나이다. 도구 호출 형식은 두 모델의 템플릿(<tool_call> JSON)이어서 Claude API의 tool_use와 같지 않다. 더 큰 모델, 사고 모드, 샘플링, Claude는 재지 않았다. 도구는 가공의 창고 세 개이고 오류는 결정적으로 짠 것이다(영구 실패는 항상, 일시 실패는 첫 호출만, 응답 유실은 첫 응답만). 실제 도구의 실패는 확률적이고 종류가 많다. 라벨 조건(R1L, R2L)은 오류의 이름도 함께 바꾸어 라벨의 효과를 분리하지 못한다. 맞는 키를 말해 주는 오류(R4, R4i)는 항상 맞는 키였다. 자동 교정이 틀렸을 때의 위험은 재지 않았다. 호출 한도는 4이고 병렬 호출은 처리하지만 따로 재지 않았다. 마지막 답의 분류와 쓰기 보고(실패, 성공, 알아챔, 다시 해 보겠다는 말)는 낱말 규칙이어서 틀린 판정이 있을 수 있고(특히 success가 '성공적으로 재시도하겠다'에도 걸린다), 수량은 정수 추출로 읽었다. 조건마다 60시행이어서 구간이 넓고(비율 0.5 근처에서 ±0.12 정도), 같은 시행 번호는 모든 조건에서 같은 세계이므로 짝지은 비교만 쓸 수 있다. 쓰기 조건은 답의 글과 하네스가 센 효과의 횟수를 따로 보았다. 여러 단계의 에이전트 평가를 최종 상태로 하는 것은 Yao 외(τ-bench)가 최종 데이터베이스 상태를 목표 상태와 견주어 평가했다고 보고한 것과 같은 방향이며(초록), 31장이 다룬다.

핵심 정리

  1. 도구 호출은 모델의 출력 글, 하네스의 파서·스키마 검사·실행, 컨텍스트로 돌아오는 결과 글로 나뉜다. 외부 세계의 효과는 도구의 실행에서만 일어나고 모델의 출력만으로는 아무 일도 일어나지 않는다. Claude API에서는 stop_reason: "tool_use"의 tool_use 블록(id, name, input)을 하네스가 실행해 tool_result(tool_use_id, content, is_error)로 돌려보낸다. 행동의 안전은 모델이 아니라 하네스가 어떤 호출을 실행하는가에 달려 있다(정의 13.1).
  2. 호출이 정답으로 이어지는 확률은 호출을 낸다, 스키마에 맞다, 인자가 맞다, 도구가 성공한다의 곱 \(\Pr[I]=p_1p_2p_3p_4\)이고, 정확도는 \(\Pr[I]\,a_I+(1-\Pr[I])/V\) 이하이다. 정답이 결과에 들어오지 않은 시행에서 값을 말하는 답은 \(1/V\) 이하로만 맞는 지어낸 답이다. 가장 낮은 단계를 고치는 것이 가장 큰 지렛대이다(정리 13.1).
  3. 인자는 복사, 유도, 추측 가운데 하나이고 추측의 상한은 \(1/V\)이다. 스키마의 enum은 후보를 줄이는 정보이지만 형식을 강제하는 strict는 \(p_2=1\)만 보증하고 값이 맞는지는 보증하지 않는다. 컨텍스트가 같으면 모델의 행동이 같으므로, 다른 레코드를 성공으로 돌려주는 도구의 오류는 결과가 키를 싣지 않으면 어떤 모델도 잡을 수 없고, 글자까지 같은 일시 실패와 영구 실패의 첫 오류에서는 모델의 다음 행동이 같다(정리 13.2).
  4. 같은 호출을 되풀이해도 영구 실패는 풀리지 않는다. 일시 실패는 \(r\)번 재시도하면 \(1-q^{r+1}\)로 성공하고 기대 호출 수는 \((1-q^{r+1})/(1-q)\)이다. 오류가 종류를 알리지 않으면 같은 호출을 되풀이하는 정책의 성공은 \(1-\rho\)에서 멈추고, 종류를 알리면 영구 실패에서 \(\rho r\)번의 호출을 아낀다. 틀린 인자에서 오류가 후보에 대한 정보를 주지 않으면 서로 다른 \(r\)개를 시도해도 성공은 \(r/N\) 이하이다. 종류를 아는 일시 실패의 재시도는 하네스가 가질 수 있다(정리 13.3).
  5. 읽기 전용, 멱등 쓰기, 비멱등 쓰기는 다시 부를 때 세계가 다르게 바뀐다(RFC 9110의 안전·멱등 구분). 응답이 유실된 쓰기의 타임아웃은 효과가 있었든 없었든 같은 컨텍스트여서 모호하고, 비멱등 쓰기를 최대 \(r\)번 다시 부르면 효과의 기댓값이 \((1-u)(1-q^{r+1})/(1-q)\)번이다. 멱등 키나 읽기로 확인한 뒤의 재시도가 중복을 막는다. MCP의 도구 주석(readOnlyHint 등)은 힌트일 뿐이고 기본값이 가장 보수적이다(정리 13.4).
  6. 실험(Qwen3-1.7B, 조건마다 60시행)에서 성공 결과를 받는 대조 조건은 정답 60/60이었다. 기본 프롬프트에서 읽기 오류 조건 10개 모두 모델은 다시 부르지 않았고(0/60), 재시도 지시를 더해도 R1, R2, R3, R4는 0/60이었다. 재시도는 오류가 '재시도 가능'이라 말한 조건(17/60)과 맞는 키로 다시 부르라고 명령한 조건(8/60)에서만 생겼고 모두 정답으로 이어졌다. 도구 결과에 없는 수를 말한 지어낸 답 90개는 모두 재고 0이었고, 다른 레코드를 성공으로 돌려준 도구의 결과는 키를 실어도 58/60이 그대로 말했다.
  7. 쓰기에서는 오류 메시지의 글이 중복을 갈랐다. 타임아웃에 retryable: true를 달자 다시 예약한 비율이 0.883(S1)과 0.700(S3)이었고, '처리되었을 수 있으니 먼저 확인하라'는 메모를 달자 60/60이 확인했고 중복이 0이었다. 아무 말이 없으면 거의 다시 예약하지 않았지만(2/60), 효과가 정확히 한 번 일어난 58개 시행 가운데 55개가 예약이 실패했다고만 말했다. 대조 모델 Qwen2.5-1.5B-Instruct는 같은 오류 글에서 재시도 지시와 retryable: true, 명령형 제안에도 4개 조건 모두 다시 부르지 않았고(0/60) 중복도 0이었다. 같은 도구와 프롬프트에서 두 모델의 반응이 달랐다. 작은 모델의 재시도와 지어내기, 쓰기 중복은 오류의 글과 하네스가 정하며, 이 결과는 가공의 도구와 모델 둘에서의 관찰이다.

확인 퀴즈

1. 모델이 {"name": "reserve_units", "arguments": {"sku": "SKU-4172", "qty": 25}}를 호출 형식으로 출력했다. 이 출력만으로 외부 세계에 일어나는 일은?

13.1절이다. 모델의 출력은 토큰의 열이고, 효과는 하네스가 \(f(a)\)를 실행할 때만 일어난다(). 그래서 같은 출력이라도 하네스가 실행을 거부하거나 확인을 요구하면 효과가 없다. 행동의 안전은 모델이 아니라 하네스의 규칙이 정한다.

2. 단계별 확률이 \(p_1=0.95\), \(p_2=0.90\), \(p_3=0.90\), \(p_4=0.80\)이고 \(V=900\)이다. 읽기가 완벽할 때(\(a_I=1\)) 정확도의 상한은?

의 1, 2번이다. \(\Pr[I]=0.95\times0.90\times0.90\times0.80=0.6156\)이고 상한은 \(0.6156+0.3844/900=0.6160\)이다. 가장 낮은 단계의 값이 아니라 곱이다. 단계가 넷이면 각각 높아 보여도 곱은 크게 줄어든다.

3. 사용자가 상품 이름만 말했다. 모델이 6자리 숫자 코드(100000~999999에서 균등)를 추측해 조회 도구를 부른다. 정확한 코드를 낼 확률의 상한은? 도구 스키마에 후보 25개의 enum을 넣고 정답이 그 안에 있다면?

의 1, 2번이다. 후보가 \(V=900{,}000\)개이면 \(1/V\)이다. 스키마의 enum은 컨텍스트에 있는 정보여서 후보를 25개로 줄이고 상한이 \(1/25=0.04\)가 된다. 형식만 강제하는 것은 후보 수를 줄이지 않는다(3번).

4. 도구 정의에 strict: true를 켜면 Claude API 문서가 보증하는 것은?

13.2절이다. 문법으로 제한한 샘플링이 형식을 보증한다(\(p_2=1\)). 값이 맞는지(\(C_3\))와 호출을 낼지(\(C_1\))는 보증하지 않는다. 문서는 일부 모델(Opus 5.5, Sonnet 5.5 등)에서 호출을 강제하는 tool_choice의 any와 tool이 400 오류를 낸다고도 쓴다.

5. 도구가 호출마다 독립으로 확률 0.4로 일시 실패한다. 같은 호출을 최대 2번 다시 부르면 성공 확률과 기대 호출 수는?

의 2번이다. 모두 실패할 확률은 \(0.4^3=0.064\)이어서 성공이 0.936이다. 기대 호출 수는 \(1+0.4+0.16=1.56\)이다. 3번을 부르는 것은 앞의 두 번이 모두 실패했을 때뿐이다.

6. 같은 도구가 영구 실패와 일시 실패 모두에서 글자까지 같은 오류 {"error": "service_unavailable"}를 돌려준다. 어떤 모델이든 첫 오류 뒤의 행동은?

의 5번과 의 3번이다. 컨텍스트가 같으면 출력의 분포가 같다. 모델의 크기가 바꾸는 것은 그 분포이지 컨텍스트에 없는 정보를 얻는 능력이 아니다. 구별하려면 오류에 종류를 싣거나(retryable) 하네스가 종류를 알아 직접 재시도해야 한다.

7. 호출은 항상 서버에 닿고 응답이 확률 0.5로 유실되는 비멱등 쓰기 도구를 타임아웃마다 최대 2번 다시 부른다. 기대 효과 횟수는? 같은 요청이 멱등 키를 싣고 서버가 같은 키를 걸러낸다면 최종 효과는?

의 2, 3번이다. \(u=0\), \(q=0.5\), \(r=2\)이면 \(\mathbb E[K]=1+0.5+0.25=1.75\)이다. 멱등 키가 있으면 호출 수와 무관하게 최종 효과가 1번을 넘지 않는다. 한 번도 닿지 못하는 경우가 없다는 가정이므로 \(u=0\)에서는 정확히 1번이다. 위 정리의 일반형에서는 닿지 못할 확률 \(u\)가 있으면 0번도 가능하다.

연습문제

단계별 확률이 \(p_1=0.99\), \(p_2=0.96\), \(p_3=0.92\), \(p_4=0.85\)이고 \(a_I=0.9\), \(V=400\)이다. (가) \(\Pr[I]\)와 정확도의 상한을 구하라. (나) 한 단계씩 완벽하게(1로) 고쳤을 때 상한이 얼마나 오르는지 구하고, 가장 먼저 고칠 단계를 고르라. (다) 읽기 \(a_I\)를 1로 올리는 것과 비교하라.

풀이

이다. (가) \(\Pr[I]=0.99\times0.96\times0.92\times0.85=0.7432\), 상한은 \(0.7432\times0.9+0.2568/400=0.6695\)이다. (나) \(C_1\)을 고치면 0.6763(+0.0067), \(C_2\)는 0.6973(+0.0278), \(C_3\)은 0.7275(+0.0580), \(C_4\)는 0.7872(+0.1177)이다. 가장 낮은 \(p_4=0.85\), 곧 도구가 성공하는 단계를 먼저 고친다. (다) \(a_I=1\)이면 0.7439(+0.0743)로 \(C_4\)를 고치는 것의 63% 정도이다. 가장 낮은 단계가 지렛대가 가장 크다.

주문 조회 도구가 ORD- 뒤에 다섯 자리 숫자(00000~99999)를 받는다. (가) 사용자가 주문 번호를 말하지 않았는데 모델이 번호를 추측해 부를 때 정확도의 상한은? (나) 도구 스키마에 이 고객의 최근 주문 50개를 enum으로 적어 두고 정답이 그 안에 있으면? (다) 스키마가 ^ORD-\d{5}$ 형식을 강제하면 (가)의 상한이 어떻게 되는가?

풀이

이다. (가) \(V=100{,}000\)이어서 \(10^{-5}\)이다. (나) 후보가 50개로 줄어 \(1/50=0.02\)이다. (다) 형식 강제는 \(p_2=1\)을 만들 뿐 후보 수를 줄이지 않아 상한은 \(10^{-5}\)로 그대로이다. 값을 맞히려면 번호가 컨텍스트에 들어와야 한다(복사). 사용자에게 되묻거나 목록을 조회하는 다른 도구를 먼저 부르는 것이다.

고객에게 안내 메일을 보내는 send_email(to, subject, body) 도구와 발송 기록을 조회하는 list_sent(to) 도구를 에이전트에 주려고 한다. (가) 두 도구를 부작용으로 분류하고, 타임아웃 뒤의 재시도 정책(누가, 언제, 몇 번)을 쓰라. (나) 타임아웃 오류 메시지에 무엇을 적을지 쓰고 이유를 대라. (다) 이 정책이 실제로 중복 메일을 막는지 재는 실험을 설계하라. 바꿀 것, 같게 할 것, 관측값, 예상과 기각 조건을 쓰라.

풀이

예시 설계이다. (가) list_sent는 읽기 전용이고 send_email은 비멱등 쓰기이다(되돌릴 수도 없다). 재시도 정책은 읽기는 하네스가 일시 실패에 한해 한도 안에서 모델 모르게 재시도하고, 메일은 타임아웃 뒤에 list_sent로 확인해 발송 기록이 없을 때만 다시 보낸다. 확인할 수 없으면 사용자에게 묻는다. (나) '요청이 처리되었을 수 있다. 다시 보내기 전에 list_sent로 확인하라'를 적는다. 의 1번이 말하듯 타임아웃의 컨텍스트에는 효과의 유무가 없으므로, 메시지가 그 불확실성과 확인 수단을 글로 넣어야 모델의 행동이 달라질 수 있다. (다) 같은 세계(수신자, 본문)에서 오류 메시지만 바꾼다(없음, '재시도 가능', 위의 메시지). 타임아웃이 반드시 한 번 나게 하고 하네스가 발송 횟수를 센다. 관측값은 수신자당 발송 횟수의 분포와 list_sent 호출 비율, 답이 실패라고 말하는 비율이다. 예상(에서): 하네스가 센 발송 횟수는 모든 시행에서 send_email 호출 수와 같다. 기각 조건: 어긋나는 시행이 하나라도 있으면 하네스의 오류이다. 중복 비율은 모델에 따라 다르므로 관찰로 보고한다. 시행 수는 중복 비율의 구간이 쓸 만하도록 조건마다 수십 번 이상 둔다.
